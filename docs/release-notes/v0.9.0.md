# EVIA Paradigma 0.9.0

STM32 boards, uploading with OpenOCD, and a new way to install: small online installers, with the toolchains
and the application itself as packages of the EVIA server that update in place.

## STM32

Five boards, each in two languages:

| Board | Chip | Core | LED | Print / Input |
|---|---|---|---|---|
| Blue Pill | STM32F103C8 | Cortex-M3, 64 MHz | PC13 (lit at LOW) | USART1: PA9 TX, PA10 RX |
| Black Pill | STM32F411CE | Cortex-M4F, 84 MHz | PC13 (lit at LOW) | USART1: PA9 TX, PA10 RX |
| Nucleo-F401RE | STM32F401RE | Cortex-M4F, 84 MHz | PA5 | USART2: the ST-Link's serial port |
| Nucleo-F411RE | STM32F411RE | Cortex-M4F, 84 MHz | PA5 | USART2: the ST-Link's serial port |
| STM32F4DISCOVERY | STM32F407VG | Cortex-M4F, 168 MHz | PD12 | USART2: PA2 TX, PA3 RX |

- **Language → STM32 C** (`--lang stm32`) writes bare-metal C: no HAL, no CMSIS, no vendor headers. The file carries
  its own register addresses, vector table and start-up code, and its linker script (in the header comment; Build
  and `--gen -o` write it as `stm32.ld`). It needs only arm-none-eabi-gcc with newlib. The clock comes from the internal
  oscillator and the PLL, so no crystal is needed; if the PLL does not start, the program runs on the internal
  oscillator with every divider following.
- Pins are `PA0` … `PI15`; `A0` … `A15` are the ADC channels (PA0–PA7, PB0, PB1, PC0–PC5), read as 0–1023 like on an
  Arduino. PWM on TIM2–TIM4 (PA0–PA3, PA6, PA7, PB0, PB1, PB6–PB9, and on the F4 also PA5 and PD12–PD15: the LEDs of the
  Nucleo and the Discovery), SPI1 on PA5–PA7, I2C1 on PB6/PB7. Every wait for the hardware has a time limit, so a
  missing device reads as -1 instead of stopping the program.
- **Language → Arduino** builds the same program as a sketch with STMicroelectronics' core (`STMicroelectronics:stm32`);
  **Settings → STM32… → Install** installs the core once.
- **Devices** has *STM32 C (bare metal)* and *STM32 Boards (Arduino)*; **File → Open Example → STM32 Boards** opens
  the board examples for them.

## OpenOCD

Upload sends either kind of STM32 program to the board with OpenOCD through an ST-Link: built into the Nucleo and the
Discovery, a separate ST-Link V2 for the Blue and Black Pill. The command is a template in **Settings → STM32…**:

    {openocd} -f interface/stlink.cfg -c "set CPUTAPID 0" -f {target} -c "program {elf} verify reset exit"

`set CPUTAPID 0` also accepts the clone chips of many Blue Pills and ST-Links. `{elf}`, `{hex}` and `{bin}` are the
program, `{device}` the serial port, so st-flash, STM32CubeProgrammer or a serial bootloader (stm32flash) can be
used instead.

## Online installers and packages

The installers are small again: the application and its own Java runtime. Everything else is a **package** of the
EVIA server at [evia.am/packages](https://evia.am/packages/index.json):

| Package | For |
|---|---|
| Arduino CLI 1.5.1 | Arduino, ESP32 and STM32 sketches (the cores come through it) |
| AVR GCC and avrdude | bare-metal AVR C |
| Arm GNU Toolchain 15.2.1 (xPack) | bare-metal STM32 C |
| OpenOCD 0.12.0 (xPack) | STM32 upload |
| OSS CAD Suite | FPGA (about 1 GB) |
| EVIA Paradigma | the application itself |

- The **first start** of an installed copy asks which toolchains to fetch for your boards (or later).
- **Settings → Packages and Updates…** (also **Help → Check for Updates…**) lists every package with the version
  installed and the one available, and installs, updates or removes them. Once a day the application quietly asks the
  server whether there are updates and says so in the status bar.
- Every download is checked against the SHA-256 the index gives before it is used, and a package is unpacked next to
  the old one and only then swapped in: a broken download changes nothing.
- The **Get** buttons of Settings fetch from the EVIA server too (from the tool's own releases if the server does not
  have it).
- Packages live in the user's data folder (`~/.evia-paradigma/packages`, `%LOCALAPPDATA%\EVIA Paradigma\packages` on
  Windows): no administrator rights.
- On the command line: `--packages` lists them, `--install ID…` installs or updates (`--install updates` takes every
  update), `--remove ID` removes one. Useful for a lab of machines, or a server without a screen.

## The application updates itself

A newer EVIA Paradigma is a package too. It installs next to the copy the installer put on the computer and is the one
that starts from then on (**Restart Now** starts it at once): the installed copy hands over to it, on the same Java
runtime. Nothing is uninstalled or installed again. If a newer version ever fails to start, it is marked and skipped,
and the version you had starts as before. `--version` says when a newer version was started this way.

## On the server

- `scripts/build-packages.sh` builds the package folder from `packaging/fetch-toolchains.sh` (every toolchain pinned
  by version and SHA-256) and the application jar, with `index.json`; `--publish /var/www/evia` installs it as
  `evia.am/packages`. Toolchain archives that are already there are kept, so a new release only adds its jar.
- The **site-dell** workflow, after every release, builds the site, serves the installers from `evia.am/downloads`
  and rebuilds the package server.

## Also

- `scripts/check-stm32.sh`: every board example for the five boards in both flows, compiled for the core by clang with
  `-Werror`; with arm-none-eabi-gcc built for real and the image checked; with QEMU, the Nucleo-F401RE builds run on an
  emulated STM32F405 against the interpreter; with the STM32 core, as Arduino sketches. In CI as the *stm32* job.
- `scripts/check-packages.sh`: install, update, a damaged download, removal and the self-update, against a package
  folder on disk.
