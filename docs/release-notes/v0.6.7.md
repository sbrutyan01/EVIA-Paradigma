## Settings → Interface language

**English**, **Русский** or **Հայերեն**. What follows the choice:

- the menu bar and every menu, the toolbar, the status line;
- the palette, including the names on the blocks themselves — a Start block reads `СТАРТ` in Russian and `ՍԿԻԶԲ` in
  Armenian, while the file it saves and the code it generates do not change at all;
- the buttons, the right-click menus, the Settings dialog and the message boxes.

The interface is redrawn when the application starts again, and Settings says so when the language changes.

**What stays in English, on purpose:** the generated code and its comments, the messages from the compilers, and the
errors the generators report for a block. A program then looks the same to everyone who opens it, whatever language
its author works in. The guide (F1) already had all three languages and is unchanged.

## How the translations work

English is the key. `Text.t("Save As...")` gives back the Russian or Armenian when one is chosen, and the English
itself otherwise — so a line nobody has translated yet simply stays English and nothing breaks.

The files are plain and tab-separated, one per language, in `src/main/resources/evia/paradigma/i18n/`:

```
Save As...	Сохранить как...
Delete block	Удалить блок
```

`scripts/i18n/collect.py` lists the strings the interface asks for and which are missing from each language, and
`scripts/check-app.sh` fails when a language falls behind. **171 strings, all translated in both.**

To add a language: copy `ru.tsv`, translate the right-hand column, add the language to `Text.Lang`. The bundled
interface font carries Latin, Cyrillic and Armenian letters already.

## New: MQTT over the chip's own Ethernet port (experimental)

Until now MQTT on a PIC32 always went through a WiFi module with AT firmware on UART2. The MX695F512L, the MX795F512L
and the **PIC32 Ethernet Starter Kit II** have an Ethernet MAC of their own, and it can now be used instead.

**Settings → PIC32 MQTT over → Ethernet, Harmony TCP/IP** (or `--net ethernet` on the command line). Only four
functions change — `rt_net_join`, `rt_net_connect`, `rt_net_write`, `rt_net_read` — so the MQTT client above them, the
blocks and the diagram are all untouched. What changes is the shape of the generated file: it becomes an **application
for an MPLAB X Harmony project** rather than a program of its own.

| | Bare metal (WiFi module) | Harmony (Ethernet) |
|---|---|---|
| Device configuration, clock | `#pragma config` in the file | the Harmony project's |
| Entry point | `int main(void)` | `void app_run(void)`, called from the project's `main()` |
| While waiting | a plain delay loop | `SYS_Tasks()` runs inside every wait, including *Delay* |
| Address | the network name and password in *MQTT Connect* | DHCP; the broker's name is resolved by the DNS client |

In **MPLAB X Harmony Configurator**, enable the TCP/IP stack with TCP, DHCP Client, DNS Client, the Ethernet MAC driver
and the board's PHY — **LAN8740** on the Ethernet Starter Kit II — then add the generated file to the project and call
`app_run()`. A chip with no Ethernet refuses the setting by name rather than generating something that cannot work.

**Experimental, and said plainly:** this output compiles against stub headers kept in this repository
(`scripts/mqtt/harmony-stubs/`, generated by `make-harmony-stubs.py`), which catches our own mistakes but cannot tell
whether the API names match the Harmony version you have. Nothing here has been built against real Harmony or run on a
board. The WiFi-module path remains the tested one. Nothing from Microchip is in this repository.

## Fixed: a program without MQTT is no longer a Harmony application

*PIC32 MQTT over: Ethernet* in Settings was applying to **every** PIC32 program, not only to the ones that
talk to a broker. A plain program built for the MX795 then came out as a Harmony application — `#include
"definitions.h"`, no `#pragma config`, no `main()` of its own — so it could only be built inside an MPLAB X
Harmony project, and `xc32-gcc` alone could not compile it.

The shape now follows the program: Harmony only when the Ethernet transport is chosen **and** the program
actually uses *MQTT Connect*. Everything else is bare-metal PIC32 C whatever that setting says. If you had
the setting on Ethernet and wondered why an unrelated program stopped building, that was this.
