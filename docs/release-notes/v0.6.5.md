# EVIA Paradigma 0.6.5

MQTT blocks: a program can now send its numbers to a broker and take commands back, on a PIC32MX chip with a WiFi
module or on an ESP32. Settings can fetch the outside tools (arduino-cli, avr-gcc, the FPGA suite) for you.

## Five MQTT blocks

In the **Board** group of the palette, next to UART, SPI and I2C:

| Block | Code | What it does |
|---|---|---|
| **MQTT Connect** | `"network", "password", "broker.example.com", 1883` | joins the network and connects to the broker |
| **MQTT Publish** | `"evia/temperature", t` | sends a message: a number or a text |
| **MQTT Subscribe** | `"evia/command"` | asks the broker for that topic (up to four topics) |
| **MQTT Has Message** | `waiting = "evia/command"` | 1 when a message is waiting, 0 when none is |
| **MQTT Read** | `cmd = "evia/command"` | the number in the next message, or -1 if none has arrived |

The network name, password, broker and topics are fixed texts, because they are written into the program when it is
built. A message is a number: *MQTT Publish* sends it the way Print writes it, and *MQTT Read* reads one back.
Negative numbers are fine — that is what *MQTT Has Message* is for, since -1 is also what *MQTT Read* gives when
nothing has arrived.

**Where the blocks work:**

- **PIC32 C** on every one of the nine chips: an ESP8266 or ESP32 module with AT firmware on **UART2**
  (RB5/RB1 on the 28-pin chips, RF4/RF5 on the others), while Print keeps UART1. The generated C drives the module
  with `AT+CWJAP`, `AT+CIPSTART` and `AT+CIPSEND`, and reads `+IPD` messages back.
- **Arduino** on an **ESP32** board: the board's own WiFi and one TCP connection, no library to install.
- **Run**: a broker on your computer. Publishing to a topic you subscribed to brings the message back, so a program
  can be tried without hardware, and the output is the same as on the board.
- An AVR board (Uno, Nano, Mega ...) refuses the blocks by name: it has one serial port and Print already uses it.
  An FPGA refuses them too.

The MQTT client itself is in the generated file: MQTT 3.1.1, quality of service 0, about 150 lines of C with no
library. `examples/boards/mqtt_sensor.evia` publishes a temperature, sends itself a command and reads it back.

## Settings fetches the tools

Next to the tool fields there are now buttons that download what is missing into EVIA Paradigma's own folder, with
no administrator rights and nothing installed system-wide:

| Tool | Where it comes from |
|---|---|
| **arduino-cli** | the Arduino project's release on GitHub |
| **avr-gcc** | Zak Kemble's AVR GCC builds |
| **OSS CAD Suite** (yosys, nextpnr, gmpack, openFPGALoader) | YosysHQ's release; one button fills in all the FPGA fields |
| **XC32** | Microchip's own page: their licence does not allow passing the compiler on, so the button opens the page and you say afterwards where it was installed |

The Windows Clang and GCC installers are unchanged.

## What was tested, and what was not

- **The MQTT packets.** New check `scripts/check-mqtt.sh` (and a CI step): the generated client is compiled on the
  computer with its network functions replaced by an ordinary socket and run against a small broker, which checks the
  CONNECT (protocol level 4), the SUBSCRIBE, and the published text and numbers, then sends messages back. All nine
  checks pass, including a negative and a fractional number.
- **The PIC32 C** of the MQTT example compiles against Microchip's real device headers for all three chip families
  and both flows, with `-Wall -Wextra -Werror` (162 of 162).
- **Run** gives the same messages as the generated program's logic; the application checks cover the blocks, the
  generated calls, the refusals and the tool catalogue.
- **Not tested:** no WiFi module, no ESP32, no PIC32 and no broker on a real network were part of this. The AT
  commands and the UART2 pins come from the datasheets and Espressif's AT documentation, not from a running board.
  The downloads in Settings were exercised against local files, not against GitHub, because this build environment
  cannot reach it.
- **Not yet:** MQTT over the Ethernet port of the MX695/795 chips. That needs a MAC driver, a PHY and a TCP/IP stack
  of its own, which is a release in itself; the WiFi module works on those chips in the meantime.
